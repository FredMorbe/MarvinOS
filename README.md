# macii.

Local hub for AI agents: routines (cron), an inbox where agents report results and ask questions, and a live overview of runs and subagents. Agents run through the official CLIs with your subscription login, no API keys.

```
npm install
npm start          # http://127.0.0.1:4747  (AIOS_PORT, AIOS_DATA to change port / data folder)
npm test
```

**Desktop app:** `app.cmd` (or `npm run app`) opens macii in an Electron window. It starts the hub itself (system `node`, like `npm start`) or attaches to one already running on the port; closing the window stops only a hub it started, so cron routines run only while the window is open. If `npm install` did not fetch the Electron binary, run `node node_modules/electron/install.js`. `start.cmd` still opens the browser version.

Requires Node 24+ (uses the built-in `node:sqlite`) and a logged-in `claude` CLI. Data (SQLite DB, raw run logs, memory graphs) lives in `data/`.

Memory graphs additionally need Graphify (Windows, needs `uv` and `git`): `npm run setup:graphify` installs the pinned release (commit `92741d1`, 0.9.95) from github.com/Graphify-Labs/graphify into `tools/graphify`.

## How it works

- **Runs:** `server/runner.js` starts `claude -p --output-format stream-json` per run, feeds the prompt on stdin and parses the stream (`server/adapters/claude.js`). At most 2 runs at once to protect the subscription limits. `ANTHROPIC_API_KEY` is removed from the child environment so a run can never silently bill the API.
- **Inbox:** each run gets an MCP server (`server/mcp/inbox-server.js`) with one tool, `inbox_send` (`result`, `question`, `approval`, `warning`). After a question or approval the run ends; your answer starts a new run with `--resume <session>`.
- **Permissions:** runs use `--permission-mode dontAsk` plus the agent's allowed tools; everything else is denied. An approval lists the exact permission patterns it needs and grants them for the resumed run only. Note: Claude Code lets some read-only shell commands (e.g. `echo`) run without being listed.
- **Subagents:** detected from `Task` tool calls in the stream (`parent_tool_use_id` builds the tree); duration and tokens per subagent. Tokens count input, cache creation and output, not cache reads.
- **Limits:** the 5h / 7d utilization shown in the header comes from the undocumented `rate_limit_event` of the CLI stream. If the CLI stops sending it, the run log shows a warning and the meters read `n/a`.
- **Limit guard:** before a scheduled run starts, `server/guard.js` compares the CLI-reported 5h / 7d utilization with your thresholds (default 85 % / 95 %, shifted per agent by priority: high +10, low −15 points). Over a threshold the run is not started, one orange warning lands in the inbox, and the run is retried 10 s after that window resets. The 7-day window is checked first. Manual starts and answers to questions are never blocked; a manual start over a threshold only shows a warning. Without data (nothing reported yet) or with a window that has already rolled over, nothing is held back. A pending retry lives in memory: restart the hub and the agent simply waits for its next cron tick.
- **Notifications:** `server/notify.js` shows a Windows toast for new inbox items and failed runs (click opens the item). It calls Windows PowerShell 5.1 with `server/toast.ps1`; the message travels as base64 JSON, never inside the script text. Toasts appear under the name "Windows PowerShell" because that app id needs no registry entry. Settings page: per-type switches and a test button.
- **Chat:** the Chat tab talks to one agent. Every message is a normal run that resumes the previous run's session (`--resume`), so the agent keeps the conversation, its folder, its tools and its memory graph. Text appears block by block when the agent finishes a block, not token by token. The agent answers in the chat; only approvals still go through the inbox (answering one continues the same chat). "New chat" starts a fresh session. **Images:** attach (Image button), paste or drop up to 4 images (PNG/JPEG/GIF/WebP, 5 MB each; bigger ones are scaled down in the browser) into the message; Claude gets them inline (`--input-format stream-json`), Codex via `--image`; they are kept in `data/uploads/`. Image files an agent mentions by path in its reply (absolute, or relative to its folder) or in a command (absolute only) are shown under that message and open full size on click. The hub serves any image file on this machine that an agent names, so only image extensions (no SVG) are served. One run per agent at a time; manual-start rules apply (never blocked by the limit guard, a warning toast instead). Claude agents only.
- **Projects:** a project is a working folder. Add one with "Add folder" on the Projects tab (type the path or press "Browse…" for a folder picker; the same picker is on the agent form and the Memory page. It lists sub-folders through `GET /api/fs`, only reachable from the app itself), also without any agent: the card offers "New agent here" (opens the agent form with the folder filled in). Folders your agents work in are added automatically. "Remove" forgets a folder that has no agents and deletes its (rebuildable) memory graph, never the folder itself. The Projects tab groups agents by folder and shows per project what runs, what waits for you, warnings, failed runs and tokens of the last 24 h. Agents sharing a folder never run at the same time: a second run waits in the queue (with a note in its log) until the first has ended, so two agents cannot edit the same files at once. Runs in different folders still run in parallel (max 2).
- **Graph modes:** the centre of the Command page has two modes (switch top left, remembered in the browser). *Memory* is the code graph of one project. *Work* shows every project (working folder) as a node, its agents orbiting it with their current task (first line of the run's prompt, or the open question / approval), the number of running subagents, and the files the agents touched in the last 10 minutes: filled dot = changed (Edit/Write), hollow = read (Read/Grep/Glob). A fresh touch draws a beam from the agent to the file. After a reload the last runs are replayed from their logged tool calls. Files touched via Bash are not shown (the shell command is opaque). In Work mode the agents hang outside their project on a slowly turning ring, each joined to the project by a line (brighter while it works). Clicking an agent (also in Memory mode) opens its chat in a modal: the Chat page in a frame without header and agent list; Esc or Close closes it, "Open in tab" continues in the Chat tab.
- **Permission modes:** each agent has one of four modes (Role tab). *Manual* = only the allowed tools run, the rest is denied and the agent asks in the inbox (CLI `dontAsk`). *Accept edits* = file edits run without asking (`acceptEdits`). *Plan mode* = the agent only reads and writes a plan, nothing in the project changes (`plan`; the plan file lands in `~/.claude/plans`). *Auto mode* = Claude's own classifier decides what is safe (`auto`; needs an account that supports it). In every mode except manual a request that would still prompt is denied (`--permission-prompts none`), because a headless run has nobody to ask.
- **Codex agents:** type `codex` runs `codex exec --json` (subscription login of the Codex app, no API key; `OPENAI_API_KEY`/`CODEX_API_KEY` are removed from the run). The executable is looked up as `AIOS_CODEX`, then `codex.exe` on PATH, then the newest `OpenAI.Codex_*` Store app (its path changes with every app update). Runs use `--ignore-user-config` on purpose: your `~/.codex/config.toml` loads desktop plugins and MCP servers, asks for approvals nobody could answer, and its model made runs stall; sandbox (`manual`/`plan` = read-only, `acceptEdits` = workspace-write), `approval_policy=never` and the Windows sandbox are set per run. The role goes in as `developer_instructions`; chat and tasks resume the thread (`exec resume`). Not yet for Codex: tool list, effort, memory graph, auto mode, questions/approvals in the inbox, limit display. `codex exec` sometimes stalls before its first answer (also outside macii); a Codex run silent for 300 s (`AIOS_CODEX_SILENCE_S`) is failed with a message instead of blocking its slot.
- **Tasks:** the Tasks tab is a board (To do / Running / Done) of work items per project folder. A task has a title, a description and optionally one Claude agent that works in that folder. "Start now" runs the agent with the task text only (title + description; the agent's role is added as system prompt, the routine prompt is not), "auto" starts it as soon as the agent is idle, the folder is free and the limit guard lets it go (oldest first, one task per agent; the reason it waits is shown on the card). The task follows its run: a question or approval turns it "asks you" until you answer in the inbox, then it continues; done, failed and stopped are shown with the run's result or error. Tasks of finished runs can be run again. Tasks are stored in SQLite (`tasks` table) and survive restarts; an automatic task that was waiting simply starts at the next check (every 30 s).
- **Memory graph (Graphify):** every agent working directory is a project. The Memory page builds its graph with `graphify extract --code-only` (local tree-sitter parsing, no LLM, no API key; `GRAPHIFY_BACKEND=none` also blocks its `claude -p` fallback). Output goes to `data/graphs/<project>/`, never into your project folder. `server/graphs.js` turns `graph.json` into a compact view (top N nodes by degree, communities named after their most connected member) and refuses an unknown `schema_version`. The Command and Memory pages draw it; a beam from an agent to a node means that agent's tool call just touched that node's file. Agents with the "memory graph" option get Graphify's read-only MCP tools (`query_graph`, `get_node`, `get_neighbors`, `get_community`, `god_nodes`, `graph_stats`, `shortest_path`); its PR tools are not allowed. Never run `graphify install` or its hooks here: they edit your assistant config.
- **Security:** binds to 127.0.0.1, rejects foreign `Host` and `Origin`, requires JSON content type for writes, and the inbox endpoint needs a per-start token that only the spawned MCP server knows.

## Not built yet

- Codex and Ollama adapters (the agent form lists them as disabled).
- Graphify: code only (docs, PDFs and images need an LLM pass and are skipped), manual rebuilds (no auto-update after runs yet), no natural-language "ask the graph" box in the UI.
- Voice control; Electron shell has no tray/background mode and no installer yet.

`mockups/` holds the original static design explorations (7 styles); the app uses the Katsumii style (`web/theme.css`).

**Light / dark mode and accent colour:** Settings > Appearance (Light, Dark, System, plus a colour picker and presets). The choice is stored per browser / desktop app in `localStorage` (`macii.theme`) and applied before the first paint by `web/theme-boot.js`, which every page loads. Colours are CSS variables: the dark values are the defaults in `theme.css`, the light ones sit in its `[data-theme="light"]` block; new UI should use the variables (`--shade-*`, `--pop`, `--on-accent`, …) and no fixed colours. An accent that would be unreadable on the current background (below 4.5:1) is darkened or lightened for display; the picked colour itself is kept. Red/yellow/orange keep their meaning in both modes. The logo has a light variant (`web/logo-h-light.png`).
